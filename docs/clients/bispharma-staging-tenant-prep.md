# Bispharma — STAGING tenant-prep plan (ent shell + users seed)

**Scope: STAGING only (F3 = `packiot_shadow`). No prod writes.** This plan makes
the staging DB *ready to receive* Bispharma data. It has two independent halves:

1. **Topology** (enterprise/site/area/equipment + packml_register) — **NOT hand-
   written and NOT executed here.** It is *generated by `onboard-gen`* from the
   filled descriptor (§1). This doc only reserves the id space and states the
   shape the generator will emit.
2. **Users seed** (Firebase UIDs → staging `users`) — independent of topology and
   can be prepared now, because the 65 users already exist on legacy prod. The
   procedure is here; the generated SQL is applied at the validation window, never
   committed (PII).

> **Do NOT execute the topology seed from this doc.** Topology comes from the
> generator once the descriptor's TODOs are filled. This is deliberate (ADR-0045
> §2.2 "generate, never hand-edit"): a hand-seeded topology drifts from the
> descriptor immediately.

---

## 0. Decision to make first — which enterprise id on staging?

Legacy **prod** Bispharma = `id_enterprise = 4` (a shell). Staging is a separate
DB with its own surrogate id space (CPACK: prod 1 → staging 3). Two options:

| Option | id on staging | Pro | Con |
|--------|--------------|-----|-----|
| **A. Reuse 4** | `enterprise_id: 4` | matches legacy; users' prod `id_enterprise` copies straight over | risk of colliding with whatever ent 4 already is on staging — **must verify staging ent 4 is free/shell first** |
| **B. Fresh id** | e.g. next free (`SELECT max(id_enterprise)+1`) | no collision risk | users' `id_enterprise` must be REMAPPED to the new id on seed |

**Action:** run the pre-check (§1a) to see what staging ent 4 currently is, then
pick. Set the chosen id into `bispharma.descriptor.yaml → enterprise_id` **and**
use it as `:ENT` throughout §2. Recommendation: **Option A if staging ent 4 is
empty/shell**, else B.

### 1a. Pre-check (staging, SELECT-only, via SSM — see memory `staging-db-access-and-config`)

```sql
BEGIN READ ONLY;
-- Is staging ent 4 free / a shell?
SELECT id_enterprise, nm_enterprise, active FROM enterprises WHERE id_enterprise = 4;
SELECT count(*) AS sites, 0 FROM sites WHERE id_enterprise = 4
UNION ALL SELECT count(*), 1 FROM areas WHERE id_enterprise = 4
UNION ALL SELECT count(*), 2 FROM equipments WHERE id_enterprise = 4
UNION ALL SELECT count(*), 3 FROM packml_register WHERE id_enterprise = 4;
-- Free id block for equipment surrogate ids (descriptor id_equipment):
SELECT max(id_equipment) AS max_equip FROM equipments;
-- Any existing users already on staging for this ent (avoid double-seed):
SELECT count(*) FROM users WHERE id_enterprise = 4;
COMMIT;
```

Pick the descriptor `id_equipment` block starting above `max_equip` (leave a gap,
e.g. start at 1001+ or the next round thousand), so generated ids never collide.

## 1. Topology — what the generator will emit (do NOT run by hand)

Once the descriptor TODOs are filled, `onboard-gen` produces `bispharma-register.sql`
(the packml_register INSERTs) and the profile. The enterprise/site/area/equipment
*rows themselves* are created as part of the onboarding apply (the generator's
register SQL assumes the equipment ids exist). The **shape** to expect on F3:

```
enterprises (1 row)   id_enterprise=:ENT, nm_enterprise='Bispharma', active=true,
                      week_begin/timezone TODO(intake — shift calendar, later)
  └── sites (1+)      id_site=?, id_enterprise=:ENT, nm_site='<site>'
      └── areas (1+)  id_area=?, id_site=?, id_enterprise=:ENT, nm_area='<area>'
          └── equipments
              • lines    tp_equipment=3, production_speed NULL (line reads own stream)
              • machines tp_equipment=1, id_unit=id_equipment,
                         production_speed=<rated>  ← REQUIRED for counters-only machines,
                         lead_machine set on the line to the first machine
packml_register        one row per topic; active=true, id_unit set for machines,
                       id_enterprise=:ENT (cross-tenant guard)
```

**Loose-ends the generator does NOT set** (fill during apply, from intake):
- `equipments.production_speed` for **counters-only** machines (intake §6). If a
  machine has no MachSpeed sensor and no rated speed, Performance can't compute.
- `equipments.status_type` — set `4` only for machines with a real state signal
  (intake §4); otherwise the EventMint scope guard applies (do NOT mint per-sample
  OPEN events for status_type≠4, or running_time overflows — feedback_bug_eventmint).
- `enterprises.week_begin / timezone / day_begin` + shifts — needed for
  shift-bucketed OEE, but NOT for the first "does data flow + OEE computes at all"
  validation. Defer to a shift-config pass.

## 2. Users seed — Firebase UIDs → staging `users`

**Why:** refdata-api resolves a browser's Firebase JWT to a tenant SERVER-SIDE via
`SELECT id_enterprise, user_roles FROM users WHERE (id_user_firebase = $1 OR
id_user_cognito = $1) AND active = true AND id_enterprise IS NOT NULL`
(`services/refdata-api/cmd/refdata-api/auth_firebase.go`). So a Bispharma user's
login only resolves once a `users` row with their `id_user_firebase` exists on
staging pointing at `:ENT`. This is exactly the front4 test-user seed pattern.

> **Note on schema:** the bootstrap `db/init/00-schema.sql` `users` table shows only
> `id_user, id_enterprise, nm_user, email, active`. The **live staging** `users`
> table additionally has `id_user_firebase`, `id_user_cognito`, and `user_roles`
> (confirmed by the auth_firebase.go SQL + task #68/#70 comments). Seed against the
> LIVE columns; verify with `\d users` in the pre-check if unsure.

### 2a. Pull the 65 from legacy PROD — SELECT-only, BEGIN READ ONLY, NEVER echo secrets

Run on **legacy prod** (read-only rule: memory `prod-db-select-only`). This
produces the seed *material*; keep it in a local scratch file OUTSIDE the repo —
**real UIDs/emails are PII and must never be committed**.

```sql
BEGIN READ ONLY;
SELECT id_user_firebase, email, nm_user, user_roles, active
FROM users
WHERE id_enterprise = 4          -- legacy prod Bispharma shell
  AND id_user_firebase IS NOT NULL
ORDER BY id_user;
COMMIT;
```

Redirect output to `~/bispharma-users.prod.tsv` (git-ignored / outside the tree).
Expect ≈65 rows. Do NOT paste the contents into any committed file, PR, or chat.

### 2b. Generate the staging seed SQL (kept out of git)

Transform the pulled rows into idempotent UPSERTs against staging, remapping
`id_enterprise` to `:ENT` (only differs from 4 under Option B). Shape:

```sql
-- bispharma-users.seed.staging.sql  (GENERATED, NOT COMMITTED — contains PII)
-- Apply on staging (packiot_shadow). Idempotent on id_user_firebase.
INSERT INTO users (id_enterprise, nm_user, email, id_user_firebase, user_roles, active)
VALUES
  (:ENT, '<nm_user>', '<email>', '<id_user_firebase>', <user_roles-or-NULL>, true),
  ...  -- one row per pulled user
ON CONFLICT (id_user_firebase) DO UPDATE
  SET id_enterprise = EXCLUDED.id_enterprise,
      active        = true;   -- re-point + reactivate if the row already exists
```

Notes:
- `ON CONFLICT (id_user_firebase)` requires the UNIQUE constraint the auth code
  relies on ("id_user_firebase is UNIQUE" — auth_firebase.go). Verify it exists on
  staging; if not, dedupe on it in the generator instead.
- `user_roles` is nullable — a NULL role still authenticates (tenant resolves; the
  two per-user-role datasets fail closed). Carry the prod value through as-is.
- **For a pilot subset** (intake §8), filter 2a to the chosen UIDs.

### 2c. Apply (validation window only)

Apply `bispharma-users.seed.staging.sql` on staging F3 during the validation
window (§ runbook). This is a **staging DML write** — allowed (staging, reversible),
unlike the prod read which is SELECT-only. Verify:

```sql
SELECT count(*) FROM users WHERE id_enterprise = :ENT AND active;   -- expect ≈65 (or pilot N)
```
