# Production promotion — the database transplant runbook

**Status:** REHEARSED on an isolated clone of the prod DB (AMI of 2026-10-08 04:13 UTC). **Nothing executed on prod.**
Executing on prod needs the user's go (2026-10-08: "rehearse, then ask me").
Tooling: `scripts/promotion/transplant/` (`build.py`, `xplant.sh`, `catalog.sql`, `05-repairs.sql`, `10-policies.sql`).
Readiness audit: [production-promotion-readiness-2026-10-08.md](production-promotion-readiness-2026-10-08.md).

## 1. Why a transplant, not a migration replay
Replaying the 143 staging-only migrations against a prod clone stopped on hand steps that no migration records:
- objects placed by hand (`gold.user_screen_config`, `mirror_replay_cursor`);
- staging was **born** with `packml_register → topic_routing` (F3 snapshot);
- the "historical — do NOT re-apply" `analytics-clean-schema` set;
- Timescale settings staging had by hand;
- staging-only tables named inside move lists.

85 failures came from about 6 roots, and completeness could only be proven by a catalog diff anyway (draft PR #1638 keeps
those findings). The transplant reaches the target **by construction**:

1. **Build.** Create `packiot_next` on the prod server from staging's `pg_dump --schema-only`, minus the staging-only objects.
2. **Copy.** Copy prod's data into it from the old DB (`postgres_fdw`, same server), applying the column renames and
   data repairs.
3. **Verify.** Check it against staging's catalog.
4. **Swap.** Rename the databases. The **old DB is never modified**, so rollback is renaming back.

## 3. Rules learned in the rehearsal (each would have broken prod)
- **OOM on the prod-sized box.** `ADD PRIMARY KEY` on a *loaded* hypertable built every chunk's index in one transaction:
  a 13 GB backend on a 16 GB r7g.large, killed by the kernel OOM killer. The prod DB box is the same size, so this would
  crash prod mid-cutover. Hypertable keys/indexes are created **before** the copy.
- **A crash is not an `ERROR:`.** The run printed none, and 29 FKs were silently missing. `xplant.sh` aborts on a psql exit
  code > 1 or "connection lost".
- `pg_dump` writes `ALTER TABLE ONLY` for keys, which Timescale rejects on hypertables.
- Timescale stores cagg definitions with unqualified names, so they need staging's DB-level `search_path` **before** the
  caggs are created.
- Prod's `equipment_values` has RLS **and** FORCE RLS; Timescale refuses caggs on it. Creating the caggs before `post`
  (where RLS is enabled) avoids that.
- zsh's builtin `echo` turns `\e` into ESC, which corrupted `\echo` lines (the repo's `analytics-clean-schema/09` has the
  same artifact). Use `printf '%s\n'`.
- `docker exec -i` inside a stdin-fed script swallows the rest of the script; pass `< /dev/null`.
- Data fixes keyed by surrogate ids don't travel: prod's PO is `1585550` where staging's replica is `101585550` (#1635).

## 5. Cutover procedure (prod)
0. Fresh inputs:
   - staging schema dump (presigned PUT, as rehearsed);
   - `catalog.sql` on staging and on prod (READ ONLY);
   - `build.py`.
   Re-run the rehearsal on a fresh AMI clone and the parity check. Snapshot the prod DB volume.
1. Announce the window. Stop the writers (ingest, stream-engine, edge-api, read-api, oeecloud-worker, Hasura) on the app box.
2. Run `xplant.sh create pre hyper views copy repair post checks data logic grants policies` on the prod DB host
   (about 2.5 min).
3. Verify (catalog + data checks from §4) and **stop if anything differs**.
4. Swap: terminate connections, then
   ```sql
   ALTER DATABASE packiot RENAME TO packiot_pre_promotion;
   ALTER DATABASE packiot_next RENAME TO packiot;
   ```
   (180 ms in the rehearsal). Restart the Timescale background workers; restart pgbouncer (the pooled
   connections cache the old `search_path`).
5. Deploy the promoted `production` branch (new images), then start the services and run the smoke tests.
6. Run `xplant.sh refresh` (about 6 min; the caggs are real-time meanwhile), then the post-cutover reviews (§6).
- **Rollback:** stop the services, swap the names back (112 ms in the rehearsal), redeploy the previous images.
  The old DB is untouched.

## 6. Decisions and follow-ups before the real run (user)
1. **CPACK configuration differs from staging on 10 columns** of `core.equipments`:
   - `event_should_be_displayed`: staging `true`, prod `NULL`. With `NULL`, the downtime list is **empty**.
   - `stop_threshold_time`: 301 vs none.
   - `minimum_*_threshold`: 30/85 vs none.
   - `downtime_reasons`: the legacy catalog vs an older shape.
   - `lead_machine` (4 lines), `gross_machine` (3), `production_speed` (13 machines).
   - `position` (display order).

   Staging's values are months of curated fixes verified against legacy. **Recommended:** carry staging's CPACK config
   (a reviewed sync step), plus `t-cpack-reason-catalog`.
2. **Retention.** Staging drops raw values after 90 days because history lives in the historian cold tier. Prod has no
   cold tier; its raw history starts 2026-08-07, so a 90-day policy would start deleting it around 2026-11-05.
   Held until decided.
3. **Prod has recorded no CPACK downtime events since 2026-08-12** (`equipment_events` max, while values are current).
   This predates the promotion; investigate the prod event path.
4. **Roles.** Prod lacks `readapi_ro`; its historian role is named `hist_gw_ro` (staging: `histgw_ro`). The rehearsal used
   `NOLOGIN` placeholders; logins and passwords come from the prod secrets at deploy.
5. **Extensions.** The new DB needs `btree_gist` (for the `EXCLUDE` constraints), `dblink` and `pg_stat_statements`.
6. **Hasura.** `hdb_catalog` lives in prod's DB; staging's has none. The `hasura` phase carries it (rehearsed: 8 tables,
   metadata intact). Retiring Hasura on prod instead is a separate decision.
7. **Post-cutover reviews:** `t-cpack-backfill-po-runtime-windows`, `t-history-uncap`, `t-cpack-reason-catalog` and
   `t-deriver-phantom-running-cleanup`. Each was computed from staging's history: rerun its detection query on prod first.
8. **Prod-only objects are left in the old DB:** 101 tables (dead `h_*`, audit tables, `*_history`, `report_*`). Nothing
   is deleted.
